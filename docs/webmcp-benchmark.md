# WebMCP benchmark：有 tool vs 沒有 tool

2026-07-28｜Chrome 151｜真實 www.kkday.com（已登入）｜每格一個**乾淨的 agent**（無前文脈絡）

兩個任務 × 兩組。兩組 prompt 逐字相同，只差一句「這個網頁透過 WebMCP 提供了 tool，優先使用」。
獨立分頁，實驗組註冊 tool、對照組不註冊。

## 結果

| | T1 探索（首頁找商品） | | T2 決策支援（商品頁讀條文） | |
| --- | --- | --- | --- | --- |
| | **無 tool** | **有 tool** | **無 tool** | **有 tool** |
| 工具呼叫 | 34 | **11** | **23** | 27 |
| tokens | 79,529 | **41,688** | **53,410** | 54,793 |
| 時間 | 8.0 分 | **2.3 分** | **3.9 分** | 4.5 分 |
| 差異 | — | **-68% 呼叫／-48% token／-72% 時間** | — | +17%／+3%／+16% |

**兩個任務的結論相反。**

## T1 探索：tool 大勝，但答案品質有天花板

無 tool 那組走 DOM：找到 SRP → 發現沒有評分篩選器 → 從 GA beacon 反推出 `count` 可調 → 撈 60 張卡 → 用 regex 拆評分價格 → 再逐一開商品頁翻日曆。34 次呼叫、8 分鐘。

有 tool 那組 11 次呼叫、2.3 分鐘拿到同一批候選。

**但正確性的勝負是分開的**（ground truth 由前一輪實測建立：迪士尼 8/15 是 2,150 不是列表的 1,755；teamLab 868 不是 710；晴空塔 631 不是 434；澀谷SKY 8/15 訂不到）：

| 檢查項 | 無 tool | 有 tool |
| --- | --- | --- |
| 說明價格是「起價」而非 8/15 價 | ⚠️ 只在括號裡帶一句 | ✅ 明確，並引用「1,755 變 2,150」 |
| 避免斷言「都在 2,000 內」 | ❌ 寫「迪士尼 1,755 剛好壓在預算內」——8/15 實際超支 | ✅ 主動警告迪士尼區間到 3,729、8/15 可能超預算 |
| 避免斷言 8/15 訂得到 | ⚠️ 驗了 1 個，其餘照推 | ✅ 明講「這一步搜尋工具做不到，得開商品頁看日曆」 |
| 說明樣本範圍 | ❌ 沒提 | ✅「596 筆裡只掃了前 60 筆，這是前段樣本」 |
| 額外查到的真實事實 | ✅ 富士山「平日方案 8/15 不開團，要選週末方案」；熱海花火 8 月只開 8/5/9/18 | ❌ 沒有（工具讀不到日曆） |

**有 tool 那組校準明顯更好**——`notes` 裡的誠實標註確實傳導到最終回答（上一輪還沒加這些警告時，同樣的 agent 就把起價當成當天價、給出一個實際超支的組合）。
**無 tool 那組換來的是真實的日曆驗證**，那是工具目前拿不到的。

## T2 決策支援：tool 沒有優勢，跟我的預期相反

我原本預期這裡 tool 會贏——12,000 字變成可按主題取用。實測**三個指標都略輸**。

原因很直接：**這一頁是 SSR，全部內容一次就在 DOM 裡**。讀 DOM 本來就便宜，包一層 tool 省不到什麼；而「先 index 再逐段取」反而多了幾次往返。

有 tool 那組的品質仍然比較好——398 階樓梯是從 FAQ 讀到的（無 tool 那組寫「頁面沒寫，是我補充的」，其實頁面有）、天上山纜車 2026 運休期 5/11–7/15 所以 8/15 不受影響、而且誠實說「`selectedDate` 是 null，我無法確認 8/15 有沒有位」。
無 tool 那組則靠實際點方案＋開日曆，做出四個方案的比較表，並抓到一個重要的坑：**頁面標題寫「五合目・天上山纜車」，但預設選中的方案不含五合目也不含纜車**。

## 順便被 agent 抓到的兩個 tool 缺陷

1. **`get_product_terms` 的 enum 承諾了它給不出來的東西。**schema 列了 `cancellation`，但這頁的 `index` 只有 description / notices / faq——取消政策其實包在購買須知裡。傳 `cancellation` 會回 error。這跟先前 `category` 的問題同一類：**schema 承諾 ≠ 實際可得**。
2. **`check_package_availability` 的 `selectedDate` 是 null 時，它答不了任何日期問題。**使用者沒在 UI 上選日期，工具就沒有日期可讀。

## 量測有效性（必須標註）

- **每格 n=1。**時間受網路與站方回應波動影響，不該當精確值看。
- **T2 有 tool 那組的成本被高估了。**它 27 次呼叫裡只有 **7 次**是真正的 WebMCP tool 呼叫，其餘 20 次是 `javascript_tool` 被 Claude in Chrome 的 `[BLOCKED: Cookie/query string data]` 過濾器擋掉後重取。這是「用 javascript_tool 手動呼叫」這個測試手法的成本，不是 WebMCP 本身的成本——真實部署下 agent 會直接呼叫 tool（例如 `chrome-devtools-mcp` 的 `execute_webmcp_tool`）。
- **實驗組被告知有 tool。**這是刻意的：先前的全盲測試顯示 agent 不會自己發現 WebMCP（67 次呼叫全程沒找到），所以那句提示是在代替「原生支援」。
- 兩組共用同一個瀏覽器、平行執行。實驗組觀察到另一分頁在變動，但未受影響。

## 結論

**WebMCP 的成本效益集中在「取代跨頁抓取」，不在「包裝單頁資料」。**

- 資料散在多頁、需要爬（列表 59 頁）→ **省 68% 呼叫、48% token、72% 時間**
- 資料本來就在同一頁 SSR（PDP 12,000 字）→ **沒有節省，甚至略增**

這推翻了我先前的排序（我曾說決策支援才是 WebMCP 現在解得掉的）。修正後的看法：

- **探索**：成本優勢明確，但答案品質的天花板在後端（掃描池 60/590、無 server 端篩選）
- **決策支援**：沒有成本優勢，價值在「有依據」與「知道自己不知道」，不在效率

而兩組共同顯示的一件事：**`notes` 裡的誠實標註是有效的**。同一個模型，在有警告時會說「這是起價、我不知道 8/15 訂不到訂得到」，在沒警告時會說「剛好壓在預算內」。這部分的投報比比任何 filter 都高。
