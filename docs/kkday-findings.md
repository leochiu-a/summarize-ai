# 實機驗證發現：前端改動提案與後端確認事項

這份是**要 KKday 這邊配合才能做的事**，不在這個 extension 的範圍內。分兩部分：
[前端可修的五項](#第一部分前端可修的五項)、[需要後端回答的問題](#第二部分需要後端回答的問題)。

**背景**：我們在評估用 WebMCP 把商品搜尋與可訂性開放給 AI agent 呼叫（讓使用者用自然語言收斂
「8/15 出發、評分 4.5 以上、兩千以內的東京行程」）。已在真實環境做過唯讀驗證，可行；剩下的事
需要你們確認才能決定要不要排。

但**第一部分的價值不依賴 WebMCP**。WebMCP 只是讓這些缺口變得更明顯——修好之後所有使用者
（含 mobile、含不用 agent 的人）都直接受益。而且**五項有四項不需要後端配合，資料早就有了，
只是前端沒用**。

**驗證環境與限制**

- Chrome 151 / `www.kkday.com` / 已登入 / 2026-07-27～29
- **全部是唯讀 GET 與 DOM 觀測，沒有任何寫入或下單**
- 只驗了兩支商品：133300（票券型，`.option-content` + `button.select-option`）與
  12319（一日遊型，`.tag-badge-wrapper` + `.kk-chip`）。**同一個 PDP 模板底下是兩套完全不同的
  DOM**，改動時兩邊都要顧
- `remain_qty` 只驗過全日型商品
- 走查資料是 2026-07-27 的，頁面隨時可能改版

## P0-1　SRP 加上「評分」篩選器（日期已有，但只在其中一種列表頁）

**現況**：`/zh-tw/product/productlist/<keyword>` 的篩選器只有 6 組（信賴商家、KKday 專屬團、
目的地、商品類別、價錢、服務保障）。**沒有日期，也沒有評分。**「東京」有 594 筆、一頁 10 筆
＝ 59 頁，使用者根本無法收斂。

> **修正（2026-08-03）**：上面那句只對**路徑型**網址成立。同一個關鍵字換成**查詢字串型**
> `/zh-tw/product/productlist?keyword=東京`，側邊欄就**多一個「出發日期」篩選器**
> （daterangepicker，實測會把東京從 594 筆收到 542 筆）。兩種網址回的是**兩套不同的模板**。
>
> 這件事本身就是個問題：同一份搜尋結果，使用者從哪個入口進來會決定他有沒有這個篩選器，
> 而路徑型正是站內連結與 SEO 常用的那一種。**建議先把「出發日期」補到路徑型模板上**——
> 後端已經支援了，缺的只是那個模板沒有掛上去。
>
> （順帶一提，這個篩選器的 input 是 `placeholder="出發日期"` 而不是有文字標籤，
> 所以掃 `innerText` 找「日期」找不到——我們自己一開始就是這樣漏掉的。
> 對螢幕閱讀器來說，placeholder 當標籤用一樣是個 a11y 問題，可以順手補 `<label>`。）

**為什麼評分現在就能做**：搜尋 API `ajax_get_product_list` 的每一筆商品本來就回這兩個欄位——

| 欄位 | 實測值 |
| --- | --- |
| `rating_star` / `rating_count` | `4.92` / `14563` |
| `earliest_sale_date` | `20260729`（⚠️ 緊湊格式，非 `YYYY-MM-DD`） |

**後端一直都給了，只是前端沒拿它們做篩選器。**

**建議**

- 先加「評分 4.5+ / 4.0+」——最單純，資料乾淨，不需要後端動
- 把「出發日期」補到路徑型列表頁（見上方修正）。**不要**改用 `earliest_sale_date` 在前端自己
  篩：它只是「最早可出發／開賣日」，不等於「那天有位」，而且實測被後端
  `filter[sale_date]` 篩掉的商品 `earliest_sale_date` 一樣是 8 月——兩者判的不是同一件事。
  真正的「那天訂得到嗎」仍需後端支援（見第二部分問題 2 與 7）
- 另外建議把每頁筆數從 10 提高（實測 `count=20` 生效、`total_page` 從 59 降到 30；上限見問題 1），
  並給分頁按鈕補 `href`（目前是純 JS，無法中鍵開新視窗、不利爬取、對鍵盤與輔具不友善）

<details>
<summary>⚠️ 實作時一定會踩到的兩個坑（我們踩過了）</summary>

**① `earliest_sale_date` 是 `20260729`，不是 `2026-07-29`。**
直接跟 `YYYY-MM-DD` 做字串比較，`'20260729' > '2026-08-15'` 恆為 true（第 5 個字元 `'0'` 的
碼位大於 `'-'`），結果**每一筆都被排除、命中永遠 0，而且不報錯**——使用者只會看到「找不到
符合的行程」然後就走了。

**② `product_category` 是 `{ main: 'CATEGORY_002', sub: [] }` 不透明代碼。**
不要拿它做「門票 / 一日遊」這種自然語言分類篩選，會永遠比不中。而 `display_tags` 裡只有
「立即確認」「1天前可免費取消」這類服務標籤，不含品類詞。需要 `CATEGORY_*` 的對照表（問題 6）。
</details>

## P0-2　方案 chip 補上 a11y 語意，並讓不可訂的方案真正 disable

**現況（實機驗證，商品 12319）**：一日遊型的方案是 `.tag-badge-wrapper > .kk-chip` radio chip，
而它們**完全沒有 a11y 語意**——

```
role           → null
aria-checked   → null
aria-selected  → null
aria-disabled  → null
tabindex       → null
pointerEvents  → auto
cursor         → pointer
選中狀態       → 只靠 class `kk-chip--selected` 表達
```

**這比走查記錄的「缺 aria-disabled」嚴重得多**：整組單選群組對輔助科技是不可見的——螢幕
閱讀器使用者無法得知這是一組選項、也無法得知目前選了哪一個。

**而且畫面會說謊。** 用可訂性 API 交叉比對同一頁的四個方案：

| pkg_oid | 方案 | 8/15 | 8 月不可訂天數 |
| --- | --- | --- | --- |
| 1466529 | 河口湖散步（銀座） | ✅ 剩 37 | 13 天（隔天交錯） |
| 1964950 | 兩人同行優惠 | ✅ 剩 41 | 5 天 |
| 1965289 | 中文導覽（銀座） | ✅ 剩 37 | 13 天 |
| **1986735** | **冬春季限定** | **❌ 不可訂** | **整個 8 月全部 31 天** |

第 4 個方案**整個 8 月完全不可訂**，但畫面上它是一個可點的 chip、沒有任何 badge。使用者要
點下去才會撞錯誤 modal，而那個 modal 叫他改日期、改日期的 modal 又叫他改方案——**循環死巷**。

**建議**

- chip 群組加 `role="radiogroup"`，每個 chip `role="radio"` + `aria-checked`
- 加 `tabindex`（選中的 0、其餘 -1），支援方向鍵切換
- 不可訂的方案：`aria-disabled="true"` + `pointer-events: none`，並在 chip 上顯示原因
  （「8 月無出團」比「該日期無法訂購」有用得多）
- **點下去撞死巷時，自動切到最接近的可用方案**，不要丟一個把責任推給另一個維度的 modal
- 系統渲染時就已經知道可訂性（badge 是算出來的），所以這是**純前端可修**

## P0-3　把剩餘庫存顯示出來

**現況**：走查記錄的痛點之一是「場次時間 dropdown 有 38 個選項、20 分鐘一檔，但**不顯示剩餘
庫存**」。

**為什麼現在就能做**：可訂性 API 每一天都回一個 `remain_qty`（完整 payload 見
[可訂性 API](#可訂性-apifetch-items-data)）。實測「剩 41 位」「剩 37 位」都拿得到，而且
**一次呼叫就回整個月的逐日資料**。

**建議**

- 月曆格與場次 dropdown 顯示剩餘數量，低於某個門檻時強調（「僅剩 3 位」）
- 這是**急迫性訊號**，對轉換有直接幫助，而且是現成資料
- 需要先確認有沒有商業或供應商合約上的顧慮（問題 B）
- ⚠️ 只驗過全日型商品（`{ fullday: n }`）。分場次商品的 key 形狀未確認（問題 C）

## P1-1　未登入被擋時導到 login 並帶 `return_url`

**現況（實機 `fetch` 探測，無 cookie）**：

| 目標 | 結果 |
| --- | --- |
| `GET /zh-tw/cart` | 302 → **`/zh-tw`（首頁）**，不是 login 頁 |
| `GET /zh-tw/booking/step1/{hash}` | 同樣 302 → `/zh-tw` |
| `GET /zh-tw/product/133300` | 200，SSR 仍渲染「加入購物車」「立即訂購」 |

**這是三家 OTA 裡最差的形狀。** Klook 至少導到 `/signin/?signin_jump=...`。

對人類：使用者被靜默丟回首頁，不知道發生什麼事、也失去原本要買的東西。
對 agent：它拿到 HTTP 200 的首頁、**零錯誤訊號**，會把首頁當成 booking 頁繼續推理。

**建議**：導到 `/zh-tw/member/login?return_url=<原本的路徑>`，登入後回到原處。
在修好這件事之前，我們不會做任何寫入型的 WebMCP tool。

## P1-2　方案卡的法律條文改成折疊

**現況**：澀谷SKY 單一方案卡內嵌約 950 字條文、佔 2 個螢幕高；USJ 的「選擇方案」區**未展開
就有 3,911 字**（全站最大單一文字區塊）。這些字剛好擺在使用者要做決定的那一刻。

**建議**：條文折疊，或移到方案展開層。決定當下只給「方案名 + 價格 + 3 個關鍵屬性」。

# 第二部分：需要後端回答的問題

## 搜尋 API（`ajax_get_product_list`）

### 我們已經自己確認的（不用回答，列出來對齊認知）

`GET /zh-tw/product/ajax_get_product_list`

已知會吃的參數：`keyword`、`currency`、`sort`、`page`、`start`、`count`、`tab_key`
（`destination=D-JP-3261` 這種結構化目的地 ID 會出現在 SRP 的 URL 上，但沒確認 API 是否也吃）

回傳形狀是**巢狀**的，商品陣列在 `data.data`：

```
{ status, isSuccess, msg,
  data: { status, data: [ …商品… ], total, saleable_product_count, page, total_page, entity_types } }
```

實測 `keyword=東京`：`total` = **590**、`count=20` 生效（`total_page` 從 59 降到 30）。

每筆商品可用的欄位（節錄，這幾個是關鍵）：

| 欄位 | 實測值範例 | 我們想拿它做什麼 |
| --- | --- | --- |
| `rating_star` / `rating_count` | `4.92` / `14563` | **評分篩選與排序**（SRP UI 目前沒有這個篩選器） |
| `earliest_sale_date` | `20260729`（⚠️ 緊湊格式） | **日期篩選**（SRP UI 目前也沒有） |
| `min_price` / `max_price` / `official_price` / `discount` | `1539` / `2841` / `50%` | 預算上限篩選 |
| `product_category` / `display_tags` | `一日遊` / `[{name:'中文導覽'}, '免費取消']` | 分類與屬性篩選 |
| `sale_status` / `purchase_type` / `purchase_date` | `ON_SALE` | 尚未使用，想知道語意 |
| `destinations` / `supplier_badge` / `is_tourism_product` | — | 尚未使用 |

**結論**：`rating_star` 與 `earliest_sale_date` 後端本來就給了。所以我們可以先在 client 端做
收斂，不必等後端加功能。以下問題是要確認「能不能做得更好」。

### 1. `count` 的實際上限是多少？

實測 `count=20` 正常回 20 筆。想知道安全上限——如果能到 50 或 100，590 筆東京商品從 30 頁降到
6～12 頁，agent 一次呼叫就能看到夠大的候選集，不必只看前 40 筆。

- 有沒有硬上限？超過會怎樣（截斷 / 報錯 / 拖慢）？
- 從你們的角度，我們該用多少才不會造成負擔？

### 2. API 能不能直接接受這些篩選參數？（**出發日期已自行找到答案**）

我們試過傳 `rating` / `min_rating` / `start_date` / `date` / `duration` / `guide_language` /
`price_min`，但連續請求後被限流，結果不可信，**所以這題我們沒有答案，不是測出來不支援**。

**更新（2026-08-03）**：出發日期這一項我們自己找到了——SRP 側邊欄本來就有「出發日期」篩選器
（`input[placeholder="出發日期"]`），它打的是**同一支 endpoint 的 POST 形狀**：

```
POST /zh-tw/product/ajax_get_product_list?keyword=…&sort=prec&page=1&count=20
Content-Type: application/x-www-form-urlencoded;charset=UTF-8
X-Requested-With: XMLHttpRequest

filter[sale_date][from]=20261105&filter[sale_date][to]=20261120&csrf_token_name=<hash>
```

實測 `keyword=東京`：594 → 542。我們已經接上了，剩下三題想確認：

1. **不合法的日期會回一個看起來成功的空結果。** 傳 `2026-11-05`（而不是 `20261105`）回的是
   HTTP 200 + `status:"success"` + `total:0`，而且 `data` 陣列被換成 `recommend_productlist`
   （搜「東京」回釜山通行證）。這跟「這個區間真的沒商品」回**完全一樣的形狀**，呼叫端無法區分。
   日期存在性也一樣沒擋：`20260230` / `20261301` 回 0 筆，而 `20261131` 會被當成 12/1
   —— 也就是**回了另一個區間的答案**。這幾種可以回明確的錯誤碼嗎？
2. **`sale_date` 實際比對的是哪個欄位／哪個概念？**（銷售期間？出發日？）見下方問題 4 的更新
   —— 它顯然不是 `earliest_sale_date`。
3. **CSRF token 只在列表頁的 SSR bootstrap 裡**（`__INIT_STATE__.state.security`），商品頁沒有。
   我們現在得從商品頁多抓一次列表頁 HTML（~1.5MB）只為了拿那 32 個字元。有沒有輕量一點的
   取得方式（例如一支只回 token 的 endpoint，或放進 meta tag）？

另外 `filter[...]` 看起來是個通用容器，如果側邊欄其他篩選器（目的地、商品類別、價錢）也走
同一組，想要一份可用 key 與值格式的清單 —— 那下面第 6 題（`CATEGORY_*` 對照表）可能就一起解決了。

還沒有答案的：**評分**（≥ 4.5）、**行程長度**（半日 / 一日 / 多日）、**導覽語言**、
**價格區間**、**目的地 ID**（`destination=D-JP-3261` 這種格式，API 吃嗎？）

如果後端支援，就交給後端做（正確且不必抓多頁）；不支援我們就在 client 端用回傳欄位篩，但那
只能篩「我們抓到的那幾頁」，會漏掉後面的商品。

### 3. `sort` 有哪些合法值？

只確認 `prec`（KKday 推薦）。SRP UI 另外有「熱門程度 / 用戶評價 / 價格低到高」，想要對應的
參數值。

目前我們刻意不猜——猜錯會拿到一份「排序看起來正常、其實是預設順序」的結果，這種錯誤沒有任何
訊號。

### 4. `earliest_sale_date` 的語意

它是「最早可出發日」還是「最早可訂日」？

這件事很重要：我們現在只能用它排除「這個日期之前根本不開賣」的商品，**不能回答「8/15 那天訂
得到嗎」**（可能已售罄或該日不出團）。有沒有辦法在列表階段就知道特定日期的可訂性？如果沒有，
那使用者問「8/15 有什麼可以玩」時，我們只能給候選再讓他一個一個點進去確認。

**更新（2026-08-03）**：第 2 題的 `filter[sale_date]` 讓這題往前走了一半——它能把候選收斂到
「這段期間有在賣」的商品（東京 594 → 542），但**還是不等於那天有位**。順帶一提，被它篩掉的
商品 `earliest_sale_date` 一樣是 8 月，所以那個欄位跟這個 filter 判的顯然不是同一件事。
想確認 `filter[sale_date]` 實際比對的是哪個欄位／哪個概念（銷售期間？出發日？）。

### 5. rate limit 政策

我們連續打十幾次之後回傳就不正常了（HTTP 200 但格式不符預期）。想知道：

- 每分鐘 / 每秒的容許量是多少？
- 被限流時回什麼？（現在看起來不是 429，我們無法區分「被限流」與「參數寫錯」）
- 如果 agent 一次呼叫要抓 3～5 頁，這樣的 pattern 可以接受嗎？

### 6. `CATEGORY_*` 代碼有對照表嗎？

`product_category` 實際上是 `{ main: 'CATEGORY_002', sub: [] }`，`main` 是不透明代碼（實測
20 筆裡出現 002 / 004 / 005 / 006 / 011 / 020），而 `display_tags` 裡只有「立即確認」「1天前可
免費取消」這類服務標籤、不含品類詞。

結果是我們無法做「只要門票類」這種篩選——試了會**永遠回 0 筆**，而且看起來像「市面上沒有這種
商品」。我們已經先把 category 參數整個移除，因為假 0 筆比沒有這個 filter 危險。

想要的是：`CATEGORY_*` → 中文品類名的對照表，或是 API 支援直接傳品類代碼篩選。順帶一問：
`sub` 實測都是空陣列，它預期會有值嗎？

### 7. 起價與特定日期價格的落差 —— 這題最重要

`min_price` 是「起價」（全期間全方案最低價）。實測 2026-08-15：

| 商品 | 列表 `min_price` | 8/15 實際價 |
| --- | --- | --- |
| 東京迪士尼樂園 & 海洋門票 | 1,755 | **2,150**（超出 2,000 預算） |
| teamLab Planets TOKYO | 710 | 868 |
| 東京晴空塔展望台 | 434 | 631 |
| 哈利波特影城 | 1,302 | 1,440 |

也就是說「起價 ≤ 2000」不等於「那天付得起 2000」。我們實測過一個 agent 只讀起價就推薦，結果
它給出的「2,000 內組合」實際加起來是 2,051，而且推薦了一個 8/15 根本還沒開賣的商品。

想問的是：**有沒有辦法在列表階段就取得指定日期的價格與可訂性？**（例如 API 吃一個日期參數，
回該日的價格與 sale status）如果沒有，我們只能在結果裡標「起價」並要求 agent 進商品頁確認——
那使用者的體驗會停在「這是候選，你自己一個一個點進去看」。

另外 `is_display_price` 這個 boolean 的語意是什麼？實測澀谷SKY 是 `false`（min=official=533），
富士山是 `true`（min 1420 / official 2841）。

### 8. 有沒有更適合的 endpoint？

`ajax_get_product_list` 是 SRP 前端在用的。如果內部有更適合程式化查詢的搜尋 API（支援更多篩選
維度、有明確的 rate limit 與版本承諾），我們寧可用那個——綁在前端 endpoint 上，你們改版我們
就會壞。

## 可訂性 API（`fetch-items-data`）

這支是後來才找到的，而且**它比搜尋 API 更有價值** —— 因為它給的東西頁面上根本看不到。

### 我們已經確認的

`GET /api/_nuxt/product/fetch-items-data`

參數：`pkgOid`、`itemOidList[]`（**必填**，不帶會回 HTTP 500）、`beginDate`、`endDate`、
`vertical`、`shouldInstantCalendar`、`previewToken`

回傳（實測商品 12319、`beginDate=2026-08-01`、`endDate=2026-08-31`）：

```
data[itemOid].calendar["2026-08-15"] = {
  date: "2026-08-15",
  is_saleable: true,
  is_sold_out: false,
  can_be_start: true,
  can_be_end: false,
  is_discounted: false,
  remain_qty: { fullday: 41 },     // ← 剩餘 41 位
  events: [...]
}
```

另有 `skusPriceCalendar`（依 SKU hash 分組）與 `closeList`。

**一次呼叫就拿到整個月**：實測 8 月共 31 天，其中 8/6、8/8、8/18、8/24、8/31 不可訂，其餘 26 天
可訂。

**兩個立刻可用的結論：**

1. **`remain_qty` 是頁面上完全沒有揭露的資訊。** 走查記錄的痛點之一是「場次時間 dropdown 不
   顯示剩餘庫存」—— API 一直都有，只是前端沒用（見 P0-3）。
2. **這支 API 可以取代「點方案 → 開日曆 → 逐格判讀」那串互動。** 我們的 benchmark 顯示對照組
   為了確認一個商品在 8/15 能不能訂，得花好幾次點擊加截圖。改用這支 API 是一次呼叫。

### A. `itemOidList` 的取得方式（已自行解決，但有後續問題）

**已解決**：`window.__NUXT__` 的方案物件裡有 `items` 欄位，就是 `item_oid` 陣列。形狀是
`{ pkg_oid: 1964950, items: [1710727], name: '...' }`，埋在 payload 深處要遞迴找、而且會重複
出現（需依 `pkg_oid` 去重）。實測商品 12319 有 4 個方案，全部查得到。

（先前我們用 regex 掃 HTML 抓到的 4 位數 2127–2130 是別的東西，真正的 `pkg_oid` 是 7 位數。）

**後續問題**：我們現在依賴 `window.__NUXT__` 的 payload 結構。這個結構算穩定嗎？如果前端重構
或升級 Nuxt 版本，`pkg_oid` / `items` 的位置與命名會變嗎？有沒有比較適合外部依賴的取得方式？

### B. `remain_qty` 可以對外顯示嗎？

如果可以，這不只是 agent 的事——**UI 直接顯示「剩 41 位」對所有使用者都有價值**，而且是現成
資料（見 P0-3）。想確認有沒有商業或供應商合約上的顧慮。

### C. `remain_qty` 的 key 是什麼語意？

實測只看到 `{ fullday: 41 }`。分場次的商品（例如澀谷SKY 20 分鐘一場）會變成
`{ "10:00": n, "10:20": n }` 這種形狀嗎？

### D. `can_be_start` / `can_be_end` 是給多日商品用的嗎？

實測 8/15 是 `can_be_start: true`、`can_be_end: false`。想確認語意，以免誤讀成「不能訂」。

### E. 這支 endpoint 在 `/_nuxt/` 底下，是內部 API 嗎？

路徑帶 `_nuxt` 看起來是前端專用的 BFF。想確認：它算穩定介面嗎？會不會隨 Nuxt 版本或前端重構
改動？有沒有比較適合長期依賴的對外版本？

## 我們這邊的自我約束（讓你們評估風險）

- 全部唯讀 GET，不會有任何寫入或下單操作
- 每頁 20 筆、預設最多抓 3 頁、硬上限 5 頁，逐頁序列請求並間隔 250ms
- 數字一律原樣沿用你們回的值，client 端只做篩選與排序，**不做任何加總或換算**
- 只暴露「SRP UI 已經有、或明顯該有」的篩選維度。不收年齡、同行人組成、身心狀況這類個人條件
  （規格層面的隱私要求，避免變成跨站個資蒐集的管道）
- 這是 desktop 的漸進增強，不是取代 SRP
