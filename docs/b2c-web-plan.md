# b2c-web 改動提案

這份是**要改 KKday 前端才能做的事**，不在這個 extension 的範圍內。

全部來自 2026-07-27 三家 OTA 走查 + 2026-07-28/29 在真實 kkday.com 上的實機驗證（唯讀）。
共同特徵：**四項有三項不需要後端配合，資料早就有了，只是前端沒用**。

而且它們的價值都**不依賴 WebMCP**。WebMCP 只是讓這些缺口變得更明顯——修好之後所有使用者
（含 mobile、含不用 agent 的人）都直接受益。

---

## P0-1　SRP 加上「日期」與「評分」篩選器

**現況**：`/zh-tw/product/productlist/<keyword>` 的篩選器只有 6 組（信賴商家、KKday 專屬團、
目的地、商品類別、價錢、服務保障）。**沒有日期，也沒有評分。**「東京」有 594 筆、一頁 10 筆
＝ 59 頁，使用者根本無法收斂。

**為什麼現在就能做**：搜尋 API `ajax_get_product_list` 的每一筆商品本來就回這兩個欄位——

| 欄位 | 實測值 |
| --- | --- |
| `rating_star` / `rating_count` | `4.92` / `14563` |
| `earliest_sale_date` | `20260729`（⚠️ 緊湊格式，非 `YYYY-MM-DD`） |

**後端一直都給了，只是前端沒拿它們做篩選器。**

**建議**
- 先加「評分 4.5+ / 4.0+」——最單純，資料乾淨，不需要後端動
- 日期篩選要**謹慎**：`earliest_sale_date` 只是「最早可出發／開賣日」，不等於「那天有位」。
  若只能用它，UI 文案要寫成「這天之後才開賣的不顯示」而不是「這天可訂」
- 真正的日期篩選需要後端支援（見 P0-1b）
- 另外建議把每頁筆數從 10 提高（實測 `count=20` 生效、`total_page` 從 59 降到 30；上限未知，
  已列進問後端的清單），並給分頁按鈕補 `href`（目前是純 JS，無法中鍵開新視窗、不利爬取、
  對鍵盤與輔具不友善）

<details>
<summary>⚠️ 實作時一定會踩到的兩個坑（我們踩過了）</summary>

**① `earliest_sale_date` 是 `20260729`，不是 `2026-07-29`。**
直接跟 `YYYY-MM-DD` 做字串比較，`'20260729' > '2026-08-15'` 恆為 true（第 5 個字元 `'0'` 的
碼位大於 `'-'`），結果**每一筆都被排除、命中永遠 0，而且不報錯**——使用者只會看到「找不到
符合的行程」然後就走了。

**② `product_category` 是 `{ main: 'CATEGORY_002', sub: [] }` 不透明代碼。**
不要拿它做「門票 / 一日遊」這種自然語言分類篩選，會永遠比不中。而 `display_tags` 裡只有
「立即確認」「1天前可免費取消」這類服務標籤，不含品類詞。需要 `CATEGORY_*` 的對照表。
</details>

## P0-2　方案 chip 補上 a11y 語意，並讓不可訂的方案真正 disable

**現況（實機驗證，商品 12319）**：一日遊型的方案是 `.tag-badge-wrapper > .kk-chip` radio chip，
而它們**完全沒有 a11y 語意**——

```
role           → null
aria-checked   → null
aria-selected  → null
aria-disabled  → null
tabindex       → null
pointerEvents  → auto
cursor         → pointer
選中狀態       → 只靠 class `kk-chip--selected` 表達
```

**這比走查記錄的「缺 aria-disabled」嚴重得多**：整組單選群組對輔助科技是不可見的——螢幕
閱讀器使用者無法得知這是一組選項、也無法得知目前選了哪一個。

**而且畫面會說謊。**用可訂性 API 交叉比對同一頁的四個方案：

| pkg_oid | 方案 | 8/15 | 8 月不可訂天數 |
| --- | --- | --- | --- |
| 1466529 | 河口湖散步（銀座） | ✅ 剩 37 | 13 天（隔天交錯） |
| 1964950 | 兩人同行優惠 | ✅ 剩 41 | 5 天 |
| 1965289 | 中文導覽（銀座） | ✅ 剩 37 | 13 天 |
| **1986735** | **冬春季限定** | **❌ 不可訂** | **整個 8 月全部 31 天** |

第 4 個方案**整個 8 月完全不可訂**，但畫面上它是一個可點的 chip、沒有任何 badge。使用者要
點下去才會撞錯誤 modal，而那個 modal 叫他改日期、改日期的 modal 又叫他改方案——**循環死巷**。

**建議**
- chip 群組加 `role="radiogroup"`，每個 chip `role="radio"` + `aria-checked`
- 加 `tabindex`（選中的 0、其餘 -1），支援方向鍵切換
- 不可訂的方案：`aria-disabled="true"` + `pointer-events: none`，並在 chip 上顯示原因
  （「8 月無出團」比「該日期無法訂購」有用得多）
- **點下去撞死巷時，自動切到最接近的可用方案**，不要丟一個把責任推給另一個維度的 modal
- 系統渲染時就已經知道可訂性（badge 是算出來的），所以這是**純前端可修**

## P0-3　把剩餘庫存顯示出來

**現況**：走查記錄的痛點之一是「場次時間 dropdown 有 38 個選項、20 分鐘一檔，但**不顯示剩餘
庫存**」。

**為什麼現在就能做**：可訂性 API 一直都有回——

```
GET /api/_nuxt/product/fetch-items-data
→ data[itemOid].calendar["2026-08-15"] = {
    is_saleable: true, is_sold_out: false,
    remain_qty: { fullday: 41 },        ← 這個
    can_be_start: true, can_be_end: false
  }
```

實測「剩 41 位」「剩 37 位」都拿得到，而且**一次呼叫就回整個月的逐日資料**。

**建議**
- 月曆格與場次 dropdown 顯示剩餘數量，低於某個門檻時強調（「僅剩 3 位」）
- 這是**急迫性訊號**，對轉換有直接幫助，而且是現成資料
- 需要先確認有沒有商業或供應商合約上的顧慮（已列進問後端的清單）
- ⚠️ 只驗過全日型商品（`{ fullday: n }`）。分場次商品的 key 形狀未確認

## P1-1　未登入被擋時導到 login 並帶 `return_url`

**現況（實機 `fetch` 探測，無 cookie）**：

| 目標 | 結果 |
| --- | --- |
| `GET /zh-tw/cart` | 302 → **`/zh-tw`（首頁）**，不是 login 頁 |
| `GET /zh-tw/booking/step1/{hash}` | 同樣 302 → `/zh-tw` |
| `GET /zh-tw/product/133300` | 200，SSR 仍渲染「加入購物車」「立即訂購」 |

**這是三家裡最差的形狀。**Klook 至少導到 `/signin/?signin_jump=...`。

對人類：使用者被靜默丟回首頁，不知道發生什麼事、也失去原本要買的東西。
對 agent：它拿到 HTTP 200 的首頁、**零錯誤訊號**，會把首頁當成 booking 頁繼續推理。

**建議**：導到 `/zh-tw/member/login?return_url=<原本的路徑>`，登入後回到原處。
在修好這件事之前，我們不會做任何寫入型的 WebMCP tool。

## P1-2　方案卡的法律條文改成折疊

**現況**：澀谷SKY 單一方案卡內嵌約 950 字條文、佔 2 個螢幕高；USJ 的「選擇方案」區**未展開
就有 3,911 字**（全站最大單一文字區塊）。這些字剛好擺在使用者要做決定的那一刻。

**建議**：條文折疊，或移到方案展開層。決定當下只給「方案名 + 價格 + 3 個關鍵屬性」。

## 這份清單的優先順序理由

| | 需要後端嗎 | 誰受益 | 建議 |
| --- | --- | --- | --- |
| P0-1 評分篩選器 | ❌ | 所有使用者 | 先做評分，日期等後端 |
| P0-2 chip a11y + 真 disable | ❌ | 輔助科技使用者 + 所有人 + agent | 純前端，一併修 |
| P0-3 顯示剩餘庫存 | ❌（要確認合約） | 所有使用者（急迫性） | 資料現成 |
| P1-1 `return_url` | ❌ | 所有使用者 | 阻擋寫入型 tool 的前置條件 |
| P1-2 條文折疊 | ❌ | 所有使用者 | 影響轉換但工程量較大 |

**前三項都不需要後端配合、資料都已經在手上。**

## 驗證方式與限制

- 全部唯讀 GET 與 DOM 觀測，沒有任何寫入或下單
- 只驗了兩支商品：133300（票券型，`.option-content` + `button.select-option`）與
  12319（一日遊型，`.tag-badge-wrapper` + `.kk-chip`）。**同一個 PDP 模板底下是兩套完全不同的
  DOM**，改動時兩邊都要顧
- `remain_qty` 只驗過全日型商品
- `/api/_nuxt/product/fetch-items-data` 路徑帶 `_nuxt`，看起來是前端專用 BFF，不是對外承諾的
  介面——如果要長期依賴，需要跟前端確認穩定性
- 走查資料是 2026-07-27 的，頁面隨時可能改版
